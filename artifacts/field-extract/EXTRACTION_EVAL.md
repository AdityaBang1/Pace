# Extraction accuracy: protocol, development split, and the recorded test number

Generated by `python -m pace.field_extract_eval --protocol-report` from the two recorded runs. The split was written to [extract_split.json](data/processed/field/extract_split.json) before any fix was written; every rule change was measured on the development split, and the test split was scored once, at the end. Rules added in later passes were measured only on development and the artifact was not re-scored, so the table below describes that recorded run, not today's code.

## The recorded test number (one touch)

**63/66 judged values correct = precision 0.955, 95% lower bound 0.887** on 12 documents from 2 institutions; 6 emitted values had no gold either way.

This is the number to quote for that run. It comes from gold that was read field by field off documents that were not in the corpus while any rule was written: two institutions are new, and every named field is judged on every document, including the fields the document does not state.

The section-span gold further down covers more documents but speaks to fewer values, and it cannot see an invented value on a field the document never states — so it is reported beside this number, never instead of it.

One gold rule matters for reading the number: Only top-level breakdown items count as grading gold. The four sub-weights on PHYS S102E ('written test' 15, 'oral test' 5, 'online section discussion' 10, 'participation' 10) are printed inside a parent category, so the rule scores them as misses when emitted. The extractor no longer emits them: a nested breakdown of a category it already returned is kept out of the top-level list, which is why this pass has 33 grading values rather than 36.

Read the bands in order — 0.70-0.90: 21/21 = 1.000, 0.90-0.99: 42/45 = 0.933. The table is **not monotone**: 0.90-0.99 (42/45 = 0.933) sits below 0.70-0.90 (21/21 = 1.000). Those bands hold enough values that the reversal is not only small-sample noise. The errors the higher band keeps are `office_hours` at 0.95 x2, `grading` at 0.90, so the remaining reversal comes from values the higher confidence cannot separate from the correct ones.

## What this pass changed, measured on the same two runs

- Value-level gold: **51/68 = 0.750** (bound 0.649) before, **63/66 = 0.955** (bound 0.887) now; 8 emitted values had no gold before, 6 now.
- Section-span gold: **10/15 = 0.667** (bound 0.423) before, **4/7 = 0.571** (bound 0.225) now. It fell, and the honest reason is coverage: the stricter rules emit 37 values on these documents before and 21 now, so only 7 values still have a span to be judged against. A 4/7 sample cannot carry a precise estimate either way.
- Confidence bands (value-level gold): 0.00-0.70 0.857, 0.70-0.90 1.000, 0.90-0.99 0.625, 0.99-1.00 0.529 before, 0.70-0.90 1.000, 0.90-0.99 0.933 now. The highest band no longer sits below the lowest one, but the table is still not monotone; the reliability section names the values that keep it from being monotone.

## The claim, in the only form this sample supports

- **Target claim:** precision 0.95 certified at 95% confidence — a false-positive rate the data can rule out at 5% or better.
- **What is certified at the shipped default (`min_confidence=0.0`):** precision no lower than **0.887** on 66 judged values.
- **What is not:** the target is not certified at *any* threshold in the table.

Every threshold above zero measures a lower bound no better than the default's, so no operating point can be set to make the target true.

That is the honest answer to the mission's reliability ask: the tool must not be described as having an operating point that certifies 0.95 precision when this sample does not support it. Each value's percentage now comes from checks on its own evidence (an explicit label, the shape the field requires, the body being about the field) rather than from the section-type softmax, and the band table above is the measurement of whether that change made the percentage mean what it says.

## What the split does and does not prove

It proves the *rules* were not tuned on the test institutions. It does not make the encoder unseen: the shipped classifier checkpoint was trained on rows from the corpus schools, so a result on those schools still leans on a model that has read them. The two institutions added for the value-level gold are not in that training set, so their numbers are the only ones in this report where neither the rules nor the encoder had seen the documents.

The test split was extracted once, in the pass that scored it, after every rule change up to that point had been measured on development; later passes fixed causes only on development and did not re-read or re-score it. The recorded artifact was then regenerated once for a reporting-only change: the section-span table now reports its own stratum, because it had been adding the value-level documents' rows into the same columns. No extraction rule, threshold or gold entry changed between those two runs; the headline and every value are identical. `extract_eval_test.previous.json` holds the previous pass's scored run (the source of the "before" numbers above) and `extract_eval_test.run1.json` the run before that.

**What this split can and cannot certify.** The value-level test gold judges 66 values. That is enough to see a cause disappear and to put a lower bound on the recorded run (0.887 at 63/66); it is not enough to certify 0.98. Even a perfect 66/66 would certify only a 0.956 lower bound, and a 0.98 bound at zero misses needs at least 149 judged values. The development split (84 judged, 77 correct, bound 0.849) can show that a rule fixed a cause or cost nothing; it cannot certify 0.98 either. No rule in this report was chosen by a headline number, and none should be: a 0.98 claim needs a larger independent gold set, not a tighter threshold.
